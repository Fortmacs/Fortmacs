2026-11-04 — `process-kill-buffer` deterministic (`process-kill-buffer-race`).  The test failed with "finished" where it expects "hangup", which looked like a flake under load, but the failing runs were all launched with `nohup`, and each one took about 100 s longer than usual.  `nohup` sets SIGHUP to ignored, and an ignored signal stays ignored through fork and exec, so the test's `sh -c "sleep 100"` (dash execs sleep) ignored the SIGHUP that `close_buffer` sent (process.c:kill_buffer_processes through process_send_signal: the pty's foreground group) and ran until the sleep ended with status 0.  Reproduced every time with `nohup tester process_mod process-kill-buffer` (100 s, "finished"); never without `nohup`, even with 8 CPU- and fork-heavy jobs running.  The code behaves like upstream: emacs_spawn resets only SIGCHLD, SIGINT, SIGQUIT, SIGPROF and SIGPIPE in the child, and sysdep.c:maybe_fatal_sig leaves an ignored SIGHUP alone in batch mode.  Interactive Emacs catches SIGHUP, so its children start with the default action.  So the test was at fault: it assumed the runner's SIGHUP handling.  It now sets SIGHUP to its default around `start_process` (new sysdep_mod `default_signal`, then `restore_signal`), as under interactive Emacs; the assertions are unchanged.  Not ported yet (unchanged): sysdep.c:init_signals' fatal-signal handlers (SIGHUP, SIGINT, SIGTERM end the editor), so an interactive Fortmacs started under `nohup` still passes the ignored SIGHUP on to its children.  Shown stable: process_mod 50 times in a row with 4 busy loops and 4 fork loops running, every other run under `nohup` (50/50 passed, none slow), plus comint_mod (13/13) and shell_mod (10/10) under `nohup`.  New hazard in PORTING.md's checklist: a signal the test runner ignores stays ignored in a child.
