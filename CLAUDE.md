# Fortmacs: instructions for Claude

Fortmacs: a rewrite of GNU Emacs 31.1 (tag emacs-31.1) in modern Fortran (2018+, gfortran).
- Reference source is upstream emacs-31.1 (tools/fetch-upstream.sh); cite the original file/function when porting. Read-only reference: never propose changes upstream.
- Behavior (commands, keys, results) mirrors vanilla Emacs 31.1 exactly: no deviations and no added features. Names, help wording and internals are Fortran-first (see the naming rule below), so Fortmacs is like Emacs but not a 1:1 copy. Anything not yet ported is listed as Deferred, never approximated. The only exceptions:
  - The Fortran configuration and generations.
  - Names use underscores where Emacs uses hyphens (commands, variables, functions, modes, hooks, keymaps, error symbols: `M-x find_file`, `C-h v fill_column`, `text_mode_hook`). When two upstream names become the same Fortran name, the plain Emacs name stays and the other gets a spelled-out suffix: `_variable` for a variable named like a function (`user_full_name_variable`), `_command` for a capitalized name that differs only in case (`buffer_menu_other_window_command`). Keys and mode-line text are unchanged.
  - Fortran-first names: Lisp-derived terms get Fortran names (defun → subprogram, sexp → expression, alist → table), each new term confirmed with the owner one by one. Confirmed renames live in tools/fortran-names, are applied with tools/fortran-names.sh and enforced by tools/check.sh; citations keep upstream names, and Lisp source text (Lisp modes, fixtures) is kept by its `keep` entries. Code ported from a new upstream version is run through tools/fortran-names.sh before review.
  - No run-time Lisp: eval-expression, eval-buffer and ielm are "Not applicable"; *scratch* starts in Fundamental mode with no Lisp message.
  - Customize and other setting-saving commands write Fortran assignments into init.f90.
  - Values are shown as Fortran (.true./.false., integers, strings, named constants); docstrings and messages carry no Lisp terms ("non-nil" becomes "true").
  - Packages are Fortran modules built in via `fortmacs --recompile`.
  - Help names the Fortran source file (simple_fm.f90).
- Target: Linux only (x86-64 and aarch64). No macOS/Windows support.
- Pure Fortran: no C source files and no C libraries beyond libc system calls, except FreeType and HarfBuzz for the GUI's fonts. Use ISO_C_BINDING only for OS/terminal I/O, sockets, threads and those two font libraries, isolated in src/sys/; hardcode Linux struct layouts and constants there. Reimplement in Fortran what upstream gets from other libraries (terminfo, X11). Project tooling is shell and awk (no Python).
- No Lisp interpreter and no Lisp-style code: always use the closest idiomatic, standard Fortran. Lisp is the reference for behavior only, never for how code looks.
  - Intrinsics and language constructs come first (`allocated`, `associated`, `present`, `size`, `len`, `any`, `all`, `findloc`, `pack`, `merge`, `index`, `scan`, `verify`, `trim`, `adjustl`, array sections, `select case`/`select type`). Never write a helper that only wraps one: no `is_null(v)` for `.not. allocated(v%a)`, `length(x)` for `size(x)`, `memq` for `any(x == y)`, `car` for `x(1)`. Flat data is plain arrays used with the intrinsics directly. tools/intrinsics.awk checks (its baseline only shrinks).
  - Settings are module variables or typed setting objects; values use intrinsic types and literals (.true./.false., integers, character).
  - Things that exist at compile time (commands, settings, modes, hooks, keymaps, faces) are named objects of derived types, changed by plain assignment to components, e.g. `commands%upcase_region%disabled = .false.`, `faces%region%background = "blue"`. Commands and faces are reached through `commands%` and `faces%` because they are separate namespaces in Emacs (both generated by tools/gen-*.sh). Per-mode objects are named after their Emacs variables (text_mode_hook, text_mode_map, text_mode_syntax_table); no major_modes%/minor_modes% in the config API. Behavior lives in type-bound procedures; functions are procedure pointers.
  - Lists are Fortran, not Lisp data: plain values in an array constructor (`completion_styles = [character(len=24) :: "basic"]`); fixed keys as typed components (`default_frame%left_fringe = 0`); records as an array of a type with fixed-length fields and keyword constructors; lists built one entry at a time through a typed `%add`. See PORTING.md "Lists in the config API".
  - Only names that exist solely at run time (e.g. typed by the user) go through a specific subroutine with intrinsic arguments, e.g. `call set_command_disabled(name, .false.)`; never generic property bags like put/get.
  - A generic Lisp value type (value_type) stays internal, only where data is truly dynamically typed, and never appears in the config API (no nil(), sym(), put(...) style).
- Port order: data structures → command loop/keymaps → terminal display → Fortran-native config API → features.
- Display: terminal first; a GUI (X11, later Wayland) after the bulk of Emacs is ported, with the protocol spoken in Fortran over a socket and fonts through FreeType and HarfBuzz. Keep redisplay independent of the output device.
- Config: a Fortran module in ~/.config/fortmacs/init.f90, statically linked into the binary; changing it means rebuilding (`fortmacs --recompile`, similar to Guix). No Elisp, no dlopen. It contains only idiomatic Fortran (assignments, pointer assignment, type-bound calls); commands that edit the init file (such as enable-command) write that form. Rebuilds are numbered generations in ~/.local/state/fortmacs/generations with a `current` symlink (build scratch in ~/.cache/fortmacs); --rollback and --list-generations come after the config API.
- Docs: FORD !> comments on every public entity; procedures of ported files say "Port of file:function" or "Not a port". tools/audit.awk (run by tools/check.sh) checks these, the file header and file names (PORTING.md, "Audit"). Ported commands, functions and variables carry the upstream docstring (adapted to Fortran names), compiled into the binary for built-in help (C-h f/k/v).
- Build with fpm. Every ported module gets a test-drive test; port the upstream ERT tests (test/src/*-tests.el) where they exist.
- CI: the full matrix (Ubuntu and Fedora on x86-64 and aarch64, Arch x86-64) on every non-draft PR and on main after each merge; Guix weekly. No runs for documentation-only pushes; a new push cancels a PR's older run. CI runs the tests: no local test runs before pushing, only the generators and the formatter (as tools/check.sh --fix does) so CI's freshness checks pass.
- Workflow: one roadmap step per PR, based on main (never stack PRs); batch related fixes into one PR rather than many small ones, and keep a PR as a draft until it is complete. When the user is away, build the next step on the open PR's branch instead of waiting for a merge. Each PR updates PORTING.md (status table) and adds its session log entry as docs/log/DATE-BRANCH.md. Never run tools/progress.sh --update-readme on a branch: the Progress workflow updates the README progress block and pie charts (docs/progress) on main after each merge. Changes to PORTING.md or CLAUDE.md always go through a PR, never straight to main. After opening a PR, poll it and continue once it is merged.
- License: GPLv3 or later, matching upstream. Ported files keep upstream FSF copyright notices plus ours.
- Keep answers short.
- When the user asks to see something (options, designs, files, answers), show it in full in the reply at that moment, before resuming other work: the user sees only replies, not text written between tool calls.

## Fortran conventions

- Style: the fortran-lang and stdlib style guides (4-space indentation, 132-column limit). fprettify formats, Fortitude lints with its default rules.
- American spelling (behavior, color, initialize) in all text, docstrings and comments; tools/check.sh checks the common British forms (tools/spelling.awk).
- Blank lines (tools/blank-lines.awk applies them; tools/check.sh checks): in a procedure body, one blank line after the declarations and one before and after every block construct (`if`, `do`, `select`, `associate`, `block`), at every nesting level and between two blocks; none between simple statements, at the start or end of a block body, or before the end of the procedure. A comment belongs to the statement below it (the blank line goes above the comment). One blank line around `contains` and between procedures, and after a section banner (a comment between two rules of dashes) between procedures. The file's header comment (its first `!` lines, before any `!>` documentation) ends with one blank line, in every Fortran file including docs/init.f90.
- Hazards (PORTING.md "Hazards"): tools/hazards.awk, run by tools/check.sh and so by CI, reports the ones a script can find; a justified exception carries `! hazard-ok(NAME): why`. Every PR is also checked by hand against that section's checklist. A newly learned hazard goes into tools/hazards.awk when a script can find it, otherwise into the checklist.
- `implicit none (type, external)` everywhere, including interface bodies; modules `private` by default with explicit `public`.
- `intent` on every dummy argument; mark `recursive` explicitly (gfortran doesn't fully default to it).
- Kinds: int64 from iso_fortran_env for buffer positions, sizes and counts (Emacs's ptrdiff_t; default integer is 32-bit in gfortran); default integer only for small values such as screen columns.
- Prefer allocatables over pointers. Reference buffers, windows and markers by integer handles into registries, not raw pointers.
- No GC: objects have explicit lifetimes (e.g. kill-buffer frees, free_marker). Handles carry a generation counter so stale handles are detected, not reused.
- Threads: one main thread owns all editor state. Background work runs on POSIX worker threads (bound in src/sys/, built with -pthread) that only see copied data and report back through a queue polled by the command loop. Worker code must be reentrant. No OpenMP or coarrays.
- No common, equivalence, goto or PDTs. No initialized local declarations (they imply `save`).
- gfortran safety: no recursive allocatable types (shallow-copy bug); never put a function result or a structure constructor inside an array constructor of a type with allocatable components (leak; use list(...), variables, element assignment or fixed-length components); never pass the same variable to two dummies when one is intent(out). `.and.`/`.or.` don't short-circuit: guard substrings and elements with a nested `if`. A function reference can't be the left side of a component assignment (`f(x)%c = v` is invalid), so compile-time objects are named variables.
- Errors: return a status/error type; no `stop` outside main. This replaces Emacs's signal/throw.
- Naming: one module per upstream file, named after it with an `_fm` suffix (buffer.c → buffer_fm, simple.el → simple_fm); file names match (buffer_fm.f90, test_buffer_fm.f90). Modules that port nothing take the suffix too (config_fm), except the user-facing API module `fortmacs`. Use a submodule when a module would otherwise form a cycle.
- Text: buffers store UTF-8 bytes (Emacs internal encoding); track char and byte positions separately (PT/PT_BYTE). Positions are 1-based, as in Emacs.
- Tooling: gfortran only (≥ 13), no second compiler; debug profile `-std=f2018 -Wall -Wextra -fcheck=all -g`.

See PORTING.md for the roadmap, the status of each module, conventions learned while porting, design decisions; the session log is in docs/log.
